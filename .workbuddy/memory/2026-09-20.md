# 2026-09-20

## 诊断：Hiddify 开代理后无法访问 google.com（仅分析，未改配置）

### 环境事实
- 运行的是**二次打包版**：进程 `HiddifyCustom.exe` (PID 25884)，
  安装目录 `C:\Program Files\Hiddify Custom\`，
  **数据/配置目录 `%APPDATA%\RenYiChun\HiddifyCustom\`**（不是 `%APPDATA%\hiddify`）。
- 关键文件：`data\current-config.json`（sing-box 生成配置）、`data\box.log`（内核日志，level=warn）、
  `data\app.log`（应用日志，含 core options）、`data\url-test.log`、`data\dynamic-direct-bypass-routes.json`、
  `rules\*.srs`、`shared_preferences.json`。
- 模式：`enableTun=false, setSystemProxy=true` → **系统代理模式，无 TUN 网卡**（已核实无 Wintun 适配器，
  默认路由仍走 WLAN 10.80.207.56）。系统代理 `HKCU\...\Internet Settings` = `http://127.0.0.1:12434`。
- 混合端口 12434（HTTP+SOCKS5 都可用）；12437=dns-in；16757=clash_api；17079/6060 非代理端口。
- 节点只有一个：`209.87.93.20`（cloudflare trace 出口 LAX/US，出网 IP 209.87.93.20）。
  并发连接 150+，节点可能是共享/高负载。
- 本机还有 Hillstone Secure Connect 企业 VPN 服务在跑；企业内网 DNS 10.80.207.56 / 172.20.50.1。

### 根因
1. **配置把 google 的 DNS 指到了国内 DNS**：
   `dns.rules` 中 `domain=[captive.apple.com, 209.87.93.20.sslip.io, api.cloudflareclient.com,
   cp.cloudflare.com, www.google.com, google.com] → server=dns-direct (tcp://223.5.5.5)`,
   `rewrite_ttl=86400`（污染结果缓存 24 小时）。
   同时 `route.default_domain_resolver = {server: dns-direct}`。
2. **本机 DNS 对 google 全面污染**（实测）：223.5.5.5→104.244.42.197(Twitter 段)、
   114.114.114.114 与 8.8.8.8→157.240.7.20(Facebook 段)、企业 DNS 10.80.207.56→185.45.5.35
   (AS35995 Twitter，实测 TCP 443 不可达)。全为伪造应答。
3. **内核日志实证**（box.log）：
   `ERROR connection: open connection to www.google.com:443 using outbound/direct[direct §hide§]:
   dial tcp 69.171.235.22:443: i/o timeout` → google 被判给 direct 直连、连伪造 IP 超时。
4. **监控全挂**（box.log）：
   `url=https://www.google.com/generate_204 total=38 success=0 failed=38 all_failed=true`；
   `url=https://cp.cloudflare.com ... all_failed=true`。
   注意：这两个探活域名**恰好就是 dns-direct 规则里的两个域名**，互相印证。
5. 但**节点本身访问 google 完全正常**：经 12434 用域名访问 `www.google.com/generate_204` 6/6 成功(204)，
   用真实 Google IP(142.251.155.119)+Host 头也 204。→ 隧道没问题，问题在 DNS/分流。

### 可能把 google 判成 direct 的规则（推断，未最终定论）
- 规则[4] `process_name` 直连名单（微信/企业微信/钉钉/微信开发者工具/FlutterPlugins/crashpad_handler 等）
- 规则[17] `rule_set: geoip-cn, geosite-cn → direct`（注：两个 .srs 仅 40KB/73KB，偏小）
- `dynamicDirectBypass=true, mode=all-direct, ttl=86400s` 动态学习直连路由
  （`dynamic-direct-bypass-routes.json` 里已含 google 系域名 `connectivitycheck.gstatic.com`）
- 规则[13] 本身是对的：`domain_suffix: google.com,... → select`（走代理）。以域名进入时能命中并可用。

### 其他发现
- `HTTP_PROXY=http://127.0.0.1:59989`（WorkBuddy 沙箱代理）会覆盖系统代理，
  在 WorkBuddy 终端里跑 curl/git 等会走它，而它对 google 返回 **502** —— 测试时容易误判。
- 分流本身工作正常：`/cn` 域名与 geoip-cn/geosite-cn 走直连（观察到大�量到国内 IP 的直连连接）。

### 建议修复方向（未执行）
1. 把 `www.google.com, google.com` 从 dns-direct 规则里移出，改走 `dns-remote`（经代理的 8.8.8.8）。
2. `default_domain_resolver` 改为 `dns-remote`，避免 sing-box 自身解析走污染 DNS。
3. 关掉 `dynamicDirectBypass` 或至少改回非 all-direct 模式，清掉已学习的直连路由。
4. 开 TUN 模式（enableTun=true）让所有程序都走代理 —— 这是系统代理模式下的根本短板。
5. 排查换掉可疑的 `geoip-cn.srs/geosite-cn.srs`。

## 环境坑（重要，复用）
- **本会话 PowerShell 工具的 stdout 不回传**（只回 exit code）。
  可靠办法：命令内 `Out-File` 写文件 → 用 Read 工具读。退出码仍可用于判断成败。
- **Git Bash 环境是坏的**：`grep/head/ls/cat/dirname/env` 全部 `command not found`（PATH 未初始化），
  不要用 Bash 工具做诊断，改用 PowerShell。
- `reg.exe` 被沙箱安全策略拉黑（Program Blacklist），读注册表改用
  `Get-ItemProperty 'HKCU:\...'`。
